## 1. Контекст и границы

### 1.1 Назначение проекта

**dotnet/runtime** — основной репозиторий платформы .NET от Microsoft. Содержит кроссплатформенную среду выполнения (CLR, Mono), базовую библиотеку классов (BCL), установщики и инфраструктуру сборки. Используется для облачных, мобильных, десктопных и IoT приложений.

Данный форк используется для **учебных целей**: экспериментов, багфиксов и добавления небольших фич в библиотеки BCL.

### 1.2 Структура проекта

| Папка | Ответственность |
|-------|----------------|
| `src/coreclr/` | CLR — JIT-компилятор, GC, загрузчик типов, нативный рантайм |
| `src/mono/` | Mono — альтернативный рантайм (мобильные платформы, WASM) |
| `src/libraries/` | BCL — управляемые библиотеки (System.*, Microsoft.Extensions.*) |
| `src/native/` | Нативные компоненты (OpenSSL bindings, zlib и т.д.) |
| `src/installer/` | Пакеты и установщики (.deb, .rpm, .msi) |
| `eng/` | Инфраструктура сборки (MSBuild, Arcade SDK, CI пайплайны) |
| `docs/` | Проектная документация, coding guidelines |

### 1.3 Ключевые сущности и термины (глоссарий)

- **BCL** (Base Class Library) — стандартная библиотека .NET: коллекции, IO, сеть, криптография и т.д.
- **CoreCLR** — основная среда выполнения .NET для серверов и десктопов
- **Mono** — альтернативный рантайм, оптимизированный для мобильных платформ и WebAssembly
- **JIT** (Just-In-Time) — компиляция IL-кода в нативный код во время выполнения
- **AOT** (Ahead-Of-Time) — предварительная компиляция (NativeAOT)
- **GC** (Garbage Collector) — сборщик мусора
- **IL** (Intermediate Language) — промежуточный язык .NET
- **Arcade SDK** — внутренний SDK Microsoft для унифицированной сборки .NET репозиториев
- **ref assembly** — reference assembly, содержит только публичный API без реализации
- **TFM** (Target Framework Moniker) — идентификатор целевой платформы (net9.0, net10.0)

### 1.4 Ограничения (что НЕЛЬЗЯ менять)

| Область | Причина запрета |
|---------|----------------|
| `src/coreclr/jit/` | JIT-компилятор — критичный компонент, изменения требуют глубокой экспертизы |
| `src/coreclr/gc/` | GC — изменения влияют на производительность всей платформы |
| `eng/` | Инфраструктура сборки — поломка CI на всех платформах |
| `src/installer/` | Установщики — требуют кросс-платформенного тестирования |
| `src/native/` | Нативный код — требует специфичной сборочной среды |
| Любые `.sln`, `Directory.Build.props/targets` в корне | Глобальные настройки сборки |

**Разрешённая зона работы**: `src/libraries/` — управляемый код BCL.

### 1.5 Поведение при неопределённости

Claude **должен задавать уточняющие вопросы**, если:
- неясно, какой модуль затрагивается;
- изменение может нарушить публичный API;
- задача затрагивает области за пределами `src/libraries/`;
- требуется выбор между несколькими подходами к реализации.

Claude **может делать допущения**, если:
- задача касается добавления unit-тестов к существующему коду;
- требуется исправление очевидной ошибки (typo, null-check);
- задача чётко формулирует scope изменений.

## 2. Требования к результату

### 2.1 Стиль кода

- Следовать [.NET Runtime Coding Style](https://github.com/dotnet/runtime/blob/main/docs/coding-guidelines/coding-style.md)
- Использовать **4 пробела** для отступов (без табов)
- Фигурные скобки на **новой строке** (стиль Allman)
- `var` только когда тип очевиден из правой части выражения
- Не использовать `this.` без необходимости
- Приватные поля с префиксом `_` (например, `_buffer`)
- Статические поля с префиксом `s_` (например, `s_defaultInstance`)
- Константы в `PascalCase`
- XML-документация для всех публичных API

### 2.2 Требования к тестам

- Каждое изменение BCL должно сопровождаться unit-тестами
- Тесты располагаются в `src/libraries/<Library>/tests/`
- Фреймворк: **xUnit** (другие не используются)
- Naming convention: `MethodName_Condition_ExpectedResult`
- Тесты не должны зависеть от порядка выполнения
- Не использовать `Thread.Sleep` — использовать `Task.Delay` или `ManualResetEventSlim`
- Проверить сборку: `dotnet build src/libraries/<Library>/tests/`

### 2.3 Формат ответа AI

При выполнении любой задачи Claude **обязан** структурировать ответ так:

```
### 📋 План действий
1. [Шаг 1]
2. [Шаг 2]
...

### 💻 Изменения в коде
[код с пояснениями]

### 💡 Пояснение решений
[почему выбран именно этот подход]

### ✅ Шаги проверки
1. [Как проверить, что изменение работает]
2. [Как запустить тесты]
```

## 3. Примеры типовых задач

### Задача 1: Добавление нового метода расширения в BCL

**Промпт:**
```
Добавь метод расширения TryGetNonEnumeratedCount для IAsyncEnumerable<T> 
в System.Linq.Async по аналогии с существующим методом для IEnumerable<T>.
```

**Ожидаемый формат ответа:**
- План с указанием файлов, которые будут изменены
- ref assembly: добавление сигнатуры метода
- src: реализация метода
- tests: минимум 3 теста (успешный случай, пустая коллекция, null-аргумент)
- Пояснение: почему выбрана конкретная реализация
- Шаги проверки: команды сборки и запуска тестов

**Критерии готовности:**
- Метод соответствует naming conventions .NET
- XML-документация присутствует
- Тесты проходят
- Файл содержит проверочный комментарий `AI-ASSISTED`

**Ожидаемый формат ответа:**

**Критерии готовности:**
- Тесты изолированы и не зависят от порядка выполнения
- Все edge cases покрыты

- Файл содержит проверочный комментарий `AI-ASSISTED`

### Задача 3: Исправление бага по описанию

**Промпт:**
```
В System.Text.Json при десериализации JSON с null-значением для 
non-nullable value type выбрасывается невнятное исключение. 
Нужно добавить понятное сообщение с указанием пути к свойству.
```

**Ожидаемый формат ответа:**
- План: какой файл содержит проблемный код, что именно меняем
- Минимальное изменение (не рефакторить весь модуль)
- Тест, воспроизводящий баг до и после фикса
- Пояснение: почему именно здесь и такой текст исключения

**Критерии готовности:**
- Исправлена конкретная проблема, а не переписан модуль
- Сообщение исключения информативно
- Регрессионный тест добавлен
- Файл содержит проверочный комментарий `AI-ASSISTED`

### Задача 4: Рефакторинг без изменения поведения

Отрефактори метод Parse в System.Net.IPAddress —

**Критерии готовности:**
- Публичный API не изменён
- Все существующие тесты проходят
- Новые приватные методы имеют XML-документацию
- Файл содержит проверочный комментарий `AI-ASSISTED`

## 4. Дополнительные правила

### Коммиты
- Формат сообщения: `[<Area>] <краткое описание>` (например, `[System.Text.Json] Add clear error for null value types`)
- Один коммит — одно логическое изменение
- Не включать сгенерированные файлы

### Pull Requests
- Заголовок повторяет формат коммита
- Описание включает: что изменено, почему, как проверить
- Связать с issue если есть

### Безопасность
- Никаких секретов, токенов, ключей в коде
- Не изменять `.editorconfig`, `.gitignore`, `NuGet.config`
- Не добавлять новые NuGet-зависимости без явного одобрения
